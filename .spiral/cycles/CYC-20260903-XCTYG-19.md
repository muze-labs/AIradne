# Cycle: Wizardly Object-Space Composition

Repository branch: `spiral/CYC-20260903-XCTYG-19-wizardly-objectspace-composition`

Branch verified: verified on 2026-09-03 at starting commit `338cf86742a0252921b3cb2273ec167e86f56cf1`; actual branch was `spiral/CYC-20260903-XCTYG-19-wizardly-objectspace-composition`.

## Analyze

Project state / prior evaluation that makes this cycle relevant:

The graph-first baseline works and passes the shared behavior contract, but human review identified a material limitation: the `ObjectSpace` class is itself one hand-built abstraction, not a composition of cleaner abstractions. Therefore the project still lacks evidence for the deeper Airadne hypothesis that a semantic core can be made small, inspectable, and compositional enough for AI-first development.

Important risk / uncertainty / desired movement:

The next step cannot be a routine refactor plan. The project needs to learn how to find correct and clean abstractions before decomposing `ObjectSpace`, otherwise the result may only split one large class into smaller arbitrary pieces.

Relevant human direction / feedback:

- Human feedback in `FBK-20260903-XCTYG-18`: `ObjectSpace` defines an abstraction, but is not itself built from cleaner abstractions.
- Human direction for this cycle: use _Programming for Wizards_ as input for learning how to get to correct and clean abstractions.
- Human caveat in `FBK-20260903-XCTYG-23`: the book was written for humans and already incorporates human language-learning cost, so its advice must be reinterpreted for Airadne's AI-first test.
- Human preference from earlier cycles: cycles may be somewhat larger when a coherent unit of learning, design, implementation, and evidence would otherwise become bookkeeping overhead.

Governing higher-level plan / direction:

Accepted design `DES-20260903-XCTYG-11` defines the graph-first publication experiment. Accepted feedback `FBK-20260903-XCTYG-18` narrows the next graph-focused work toward compositional object-space design.

Current position in that plan:

The conventional baseline and first graph-first baseline exist. This cycle prepares and, after confirmation, can implement the next graph-focused step: decomposing object-space behavior into cleaner primitives while preserving the shared publication behavior contract.

## Plan

### Cycle Goal

Learn and record the abstraction-finding method from _Programming for Wizards_, apply it to the current `ObjectSpace` pressure points, and produce a confirmed compositional design before changing the graph implementation.

### Commitment Boundary

The cycle may create source, understanding, and design artifacts immediately. It must not refactor the graph implementation until the design is accepted or corrected by the human.

### Why Now / Why This Cycle Boundary

This cycle is larger than a single artifact because the source intake, interpretation, and object-space design are one causal move. It is still narrower than changing the runtime: the code change should wait until we have agreement on what counts as a clean abstraction in this project.

### Current Starting Evidence

- `DES-20260903-XCTYG-11` defines the graph-first experiment and the shared behavior surface.
- `EVD-20260903-XCTYG-17` verifies that the graph-first baseline passes the current behavior contract.
- `FBK-20260903-XCTYG-18` identifies the missing compositional-abstraction evidence.
- _Programming for Wizards_ chapters are available at `https://github.com/poef/programming-for-wizards/tree/main/content/chapters`.

### Evaluation Basis

The planning part of the cycle is successful when:

- a pinned source artifact records the relevant book chapters used as input;
- an understanding artifact states the abstraction method in Airadne terms;
- a design artifact identifies the clean primitives to extract from `ObjectSpace`;
- the design includes falsification checks, not only implementation tasks;
- the human can accept, reject, or correct the design before implementation.

If implementation continues in this same cycle after acceptance, the implementation part is successful when:

- the shared publication behavior contract still passes;
- new primitive-level tests verify the extracted object/fact/index/traversal boundaries;
- `ObjectSpace` becomes a small facade or disappears;
- domain rules such as authorization, validation, and behavior selection do not move into the graph kernel;
- verification evidence records whether the decomposition actually improved inspectability.

### Explicit Non-Goals

- Do not introduce a parser, external DSL, persistence layer, command log, UI, or generated runtime.
- Do not change the publication fixture semantics.
- Do not assume that every helper function deserves to become an abstraction.
- Do not claim the full Airadne hypothesis from a decomposition that only moves complexity around.

### Pause / Re-Plan Conditions

- The book-derived method points away from decomposing `ObjectSpace` now.
- The proposed primitives do not correspond to different change pressures.
- The design would hide graph meaning behind a new vocabulary that has not earned its cost.
- Human review rejects or materially changes the proposed abstraction boundaries.
