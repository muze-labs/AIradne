## Plan

### Cycle Goal

Implement the shared publication fixture and conventional explicit-code baseline, with tests and explanation outputs for the required query, mutation, validation, authorization, and contextual behavior surface.

### Commitment Boundary

Human confirmation in conversation on 2026-09-03 to start the next cycle from `main`. Accepted design input: `DES-20260903-XCTYG-11`.

### Why Now / Why This Cycle Boundary

This cycle is intentionally larger than artifact-only cycles. It should produce both implementation and evidence for one coherent control condition. It is still bounded because it implements only the conventional explicit-code baseline, not the graph-first kernel or commanded dataspace versions.

### Plan Continuity Decision

Continue from the accepted experiment design. The cycle implements representation A only and keeps hierarchy as a projection over stable IDs.

### Current Starting Evidence

- `DES-20260903-XCTYG-11` defines the shared fixture, required behaviors, compared representations, and evaluation tasks.
- `EVD-20260903-XCTYG-8` says conventional explicit code must remain a serious baseline.
- `FBK-20260903-XCTYG-9` says hierarchy must not become identity.

### Evaluation Basis

The cycle is successful when:

- shared fixture data exists in project code;
- conventional explicit-code baseline implements the required behavior surface;
- tests cover visible pages, referenced assets, navigation projection, topic listing, visibility explanation, mutations, validation, authorization denial explanation, and behavior precedence;
- implementation evidence records what was built, what was verified, and where complexity landed;
- no graph-first kernel, commanded dataspace implementation, DSL, or framework commitment sneaks in.

### Likely Work

- Add a minimal Node.js project using built-in `node:test`.
- Add shared fixture data with stable IDs and typed relation records.
- Add conventional baseline modules with explicit functions over the fixture.
- Add tests for the required behavior surface and explanation outputs.
- Record implementation and verification evidence artifacts.
- Evaluate the cycle and leave it for human review.

### Explicit Non-Goals

- Do not implement graph-first object-space kernel.
- Do not implement commanded dataspace kernel.
- Do not design a DSL grammar.
- Do not choose a production framework or storage engine.
- Do not add UI/editor scope.
- Do not add external dependencies unless plain Node.js proves insufficient.

### Pause / Re-Plan Conditions

- The required behavior surface cannot be implemented cleanly without turning the baseline into a hidden framework.
- The design fixture is ambiguous enough that implementation would silently choose semantics the design should define.
- Tests reveal the design protocol is inconsistent.
