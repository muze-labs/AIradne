## Plan

### Cycle Goal

Implement the graph-first object-space kernel against the same publication fixture and behavior surface as the conventional baseline, with tests and explanation outputs sufficient to compare representation B against representation A.

### Commitment Boundary

Human confirmation in conversation on 2026-09-03 to proceed with the proposed graph-first object-space baseline cycle.

### Why Now / Why This Cycle Boundary

This is the smallest coherent next comparison: one new representation plus verification evidence. It is intentionally larger than a single artifact and intentionally narrower than adding commanded dataspace, DSL syntax, generated runtime, persistence, or UI.

### Plan Continuity Decision

Continue from the accepted experiment design. Preserve the rule that stable object IDs are identity and `contains` is only a projection relation.

### Current Starting Evidence

- `DES-20260903-XCTYG-11` defines representation B and the shared experiment protocol.
- `IMP-20260903-XCTYG-13` provides the conventional explicit-code baseline.
- `EVD-20260903-XCTYG-14` verifies the baseline with 13 passing tests.
- `FBK-20260903-XCTYG-9` says hierarchy must not become identity.

### Evaluation Basis

The cycle is successful when:

- a graph-first object-space kernel exists in project code;
- it uses stable IDs, typed relation facts, indexes, projection traversal, validation rules, behavior rules, and authorization rules;
- it implements the same behavior surface as the conventional baseline;
- tests cover the shared behavior surface for both baseline and graph-first representation;
- explanation outputs are at least as structured and inspectable as the conventional baseline;
- implementation and verification evidence are recorded;
- no commanded dataspace, DSL grammar, generated runtime, persistence, or UI is introduced.

### Likely Work

- Add a graph-oriented store/kernel module over the existing fixture shape.
- Add a graph-first representation module exposing the same behavior API as the conventional baseline.
- Extract a shared behavior contract test helper if useful to avoid duplicating assertions.
- Add representation-specific tests for graph-kernel explanation shape.
- Run `npm test` and project-local Turtle parsing.
- Record implementation and verification evidence.
- Evaluate the cycle for human review.

### Explicit Non-Goals

- Do not implement the commanded dataspace representation.
- Do not design DSL syntax.
- Do not add generated runtime code.
- Do not add persistence, UI, deployment, or external dependencies.
- Do not change the accepted fixture semantics unless tests reveal a contradiction.

### Pause / Re-Plan Conditions

- The graph-first implementation cannot reuse the same fixture semantics without changing the design.
- The shared test contract hides meaningful differences between representations.
- The kernel grows large enough that it is no longer a small semantic candidate.

What changed in our understanding:

The graph-first approach makes explanation paths more inspectable, but the kernel/domain split itself becomes a concept future agents must understand. For this slice, graph-first buys trace shape more than brevity.

Human review sharpened the next hypothesis: to test the full idea, the object-space layer itself must be built from smaller cleaner abstractions rather than appearing as one hand-coded class.

Surprises / model mismatches:

The graph-first implementation needed more code than the conventional baseline immediately: `src/graph-object-space.cjs` is 544 lines versus `src/conventional-baseline.cjs` at 381 lines. The project should not assume semantic approaches win on size.

Known compromises:

The graph-first representation is still plain JavaScript and in-memory. It does not include a query language, persistence, command log, fresh-agent handover measurement, independent semantic interpreter, or compositional decomposition of `ObjectSpace`.

Unresolved issues within current goal:

None blocking this cycle. The result is accepted as a valid graph-first baseline, but not as a complete test of Airadne's deeper compositional-abstraction hypothesis.

## Process Learning

What context/constraint/evaluation helped:

- The accepted experiment protocol and the conventional baseline made it clear when graph-first behavior matched the same surface instead of quietly changing the problem.

What bookkeeping was useless:

- None identified. Keeping implementation and evidence in one cycle was a better size than artifact-only cycles.

What should the environment learn from this cycle:

- When adding new representations, use shared behavior contract tests plus representation-specific explanation/trace tests.
- Track implementation-size counterpressure as evidence, but do not treat line count as the success metric.
- Do not claim Airadne's full semantic-core hypothesis from an abstraction that is not itself built out of cleaner abstractions.
