# Source: Greenfield Intake For AI-First Architecture Exploration

## Source Kind

Connected conversation / retained human-authored intake.

## What Was Actually Expressed Or Observed

The project should investigate a new software architecture for AI-first development.

The starting observation is that many current software systems are optimized for human programmers working in a small number of familiar general-purpose languages. That encourages large codebases, framework conventions, repetition, and abstraction structures that humans can navigate incrementally.

AI developers have different constraints.

They do not have a strong need to remain within a small set of familiar programming languages, but they do have limited working context. A smaller executable semantic model may therefore have substantial advantages for AI reasoning, handover, verification, and maintenance.

The hypothesis is:

> A software system designed around a very small semantic core plus compact domain-specific languages may be easier for AI developers to understand, modify, verify, and hand over than a conventionally structured system, even when those DSLs would impose an undesirable learning cost on human developers.

This project should investigate that hypothesis rather than assume it is true.

## Relevant Prior Work

### VPRI / STEPS

VPRI explored whether a complete personal computing environment could be expressed in roughly 20,000 lines of meaningful code by using powerful abstractions and domain-specific languages.

This project is interested in revisiting that direction under a changed assumption: much of the software may now be developed and maintained by AI rather than directly by human programmers.

The target is not a particular LOC number. A more useful goal may be keeping the executable semantic model small enough that an AI can reason about most or all of the relevant system at once.

### Ariadne

Ariadne CMS has been developed and used for more than 25 years and contains several ideas that appear to have survived substantial technological change.

The project does not want backwards compatibility with Ariadne and should not use its current implementation as an oracle. Ariadne should be treated as historical evidence.

The project wants to identify which concepts proved genuinely useful over decades of use, which were accidental consequences of their era, and which caused persistent problems.

Possible durable concepts include:

- a uniform navigable object space;
- stable object identity and hierarchy;
- separation between objects and behaviour;
- contextual behaviour override / acquisition;
- behaviour selection based on both type and context;
- flexible object data combined with indexed/searchable properties;
- hierarchical authorization/capabilities.

None of these should be accepted without examination.

### SimplyStore

SimplyStore is a separate modern investigation into small, durable data infrastructure.

It already explores ideas such as:

- a deliberately small storage core;
- command logs;
- reconstruction from authoritative state;
- independently derived indexes;
- explicit durability and integrity boundaries.

SimplyStore is currently designed primarily for human developers.

It may be suitable as a substrate for this experiment, but this should also be treated as a hypothesis rather than a constraint.

## Research Question

The central question is:

> What software architecture emerges if AI context size, AI reasoning reliability, explicit semantics, and auditability are treated as first-class design constraints?

Secondary questions include:

- Does semantic compression actually reduce the context needed for correct changes?
- When does a DSL remove complexity, and when does it merely hide complexity?
- How small can the trusted semantic kernel remain?
- Can the complete semantics of the DSLs be stored alongside the project and cheaply learned by an unfamiliar AI?
- Does this improve AI handover between models or providers?
- Can humans still meaningfully inspect, review, and challenge the resulting software?
- Does a small semantic model improve causal explanation and provenance?
- What kinds of functionality should remain conventional code rather than become DSL constructs?
- Does separating generated/optimized implementation from meaningful source improve or reduce trust?

## Important Constraints

- Do not begin by designing a programming language.
- Do not begin by rewriting Ariadne.
- Do not assume SimplyStore must be used.
- Do not optimize primarily for LOC.
- Do not introduce a DSL merely because it makes examples shorter.
- Do not assume current web architecture patterns such as REST controllers, ORMs, frontend frameworks, dependency injection, or microservices are inherently desirable.
- Do not reject conventional web architecture patterns merely because they are conventional.

The objective is to discover the smallest useful semantic system supported by evidence.

## Desired Properties

Candidate designs should preferably support:

- small explicit semantics;
- deterministic or inspectable behaviour;
- excellent introspection;
- strong invariants;
- local reasoning;
- minimal hidden state;
- machine-readable structure;
- causal traceability;
- provenance;
- independent verification;
- easy reconstruction;
- model/provider handover;
- human auditability.

A useful distinction is:

> generated code may be large, but independent meaning should remain small.

Generated or optimized machinery is acceptable when its behaviour is mechanically derived from a smaller authoritative representation.

## Initial Investigation

Start with evidence gathering rather than implementation.

Investigate three areas:

1. Ariadne experience.
2. SimplyStore.
3. Minimal semantic experiments.

For Ariadne, identify concrete examples of things Ariadne made unusually easy, abstractions that remained useful for many years, behaviours reused across unrelated applications, concepts developers relied on rather than worked around, concepts that caused confusion or fragility, and features whose usefulness disappeared as surrounding technology changed.

Translate observations into candidate architectural properties. Do not preserve Ariadne terminology when a more fundamental property can be identified.

For SimplyStore, examine which properties are useful as foundational primitives and which exist mainly to make the system pleasant for human programmers. Ask whether an AI-first layer above SimplyStore could expose substantially smaller semantics without compromising correctness or auditability.

For minimal semantic experiments, identify one small but meaningful vertical slice suitable for testing competing architectures. Prefer a slice involving several interacting concerns, such as structured objects, relationships/hierarchy, queries, mutation, validation, authorization, contextual behaviour, and frontend/backend interaction.

## Evaluation

Any proposed DSL or semantic abstraction should answer:

1. What complexity does this remove?
2. Where did that complexity go?
3. What new hidden semantics does this introduce?
4. How much source must an unfamiliar AI inspect to safely change behaviour?
5. Can the AI explain the causal path from requirement to observable behaviour?
6. Can a human inspect that explanation?
7. What is the blast radius of changing one language primitive?
8. How can the primitive be independently tested or falsified?
9. Can the application survive replacement of the AI model/provider without reconstructing large amounts of implicit context?
10. Would ordinary code be simpler here?

## Spiral Developer Stance

Treat this as an exploration.

Do not convert an attractive idea directly into implementation.

Record assumptions, hypotheses, evidence, counterexamples, rejected alternatives, unresolved questions, risk, and confidence.

Challenge the framing where appropriate. In particular, actively attempt to falsify the core hypothesis that smaller semantic systems improve AI software development.

The first useful output is not a design.

The first useful output is a map of likely durable concepts, questionable assumptions, competing architectural directions, highest-risk unknowns, and cheapest experiments capable of distinguishing between them.
